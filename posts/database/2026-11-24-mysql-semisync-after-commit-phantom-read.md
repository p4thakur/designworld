Primary.
  - There is no `wait_point` variable. The only waiting hook is `repl_semi_report_commit`, registered as `// after_commit`.
  - The timeout is `MYSQL_SYSVAR_ULONG(timeout, rpl_semi_sync_master_timeout, ... "The timeout value (in ms) for semi-synchronous replication in the master" ... 10000, 0, ~0UL, 1)`.
- mysql/mysql-server tags `mysql-5.7.1` and `mysql-5.7.2`, `plugin/semisync/semisync_master_plugin.cc`. Primary. 5.7.1 has 0 occurrences of `wait_point`. 5.7.2 adds `MYSQL_SYSVAR_ENUM(wait_point, ...)` with `WAIT_AFTER_SYNC, /* default */`. The 5.7 description says AFTER_SYNC "guarantees that no other sessions can see the data before replicated to slave. AFTER_COMMIT means that semisynchronous replication waits just after the engine commits. Other sessions may see the data before it is replicated, even though the current session is still waiting for the commit to end successfully."
- mysql/mysql-server branch `8.0`, [plugin/semisync/semisync_source_plugin.cc](https://raw.githubusercontent.com/mysql/mysql-server/8.0/plugin/semisync/semisync_source_plugin.cc). Primary.
  - `repl_semi_report_binlog_sync` calls `commitTrx` only when `wait_point == WAIT_AFTER_SYNC`. `repl_semi_report_commit` calls it only when `wait_point == WAIT_AFTER_COMMIT`.
  - The wait_point help text: AFTER_SYNC "waits for the replies just after it has synced the binary log file (or would have synced, but may have skipped it, when sync_binlog!=1), but before it has committed in the engine... it guarantees that no other sessions on the source can see the effects of the transaction before the replica has received it."
  - The timeout help text: "If less than rpl_semi_sync_source_wait_for_replica_count replicas have replied after this amount of time, switch to asynchronous replication." The default is 10000.
- mysql/mysql-server branch `8.0`, [plugin/semisync/semisync_source.cc](https://raw.githubusercontent.com/mysql/mysql-server/8.0/plugin/semisync/semisync_source.cc). Primary.
  - In `commitTrx()`, a failed `mysql_cond_timedwait` is commented "This is a real wait timeout." It increments `rpl_semi_sync_source_wait_timeouts` and calls `switch_off()`.
  - `switch_off()` sets `state_ = false`, increments `off_times` (status `no_times`), and runs `signal_waiting_sessions_all()`.
  - `commitTrx()` ends with `return function_exit(kWho, 0);` and increments `no_transactions` (status `Rpl_semi_sync_source_no_tx`) when semi-sync is off.
  - `try_switch_on()` turns semi-sync back on when the binlog dump thread's position reaches the largest commit position.
- MySQL Bug [#62174](https://bugs.mysql.com/bug.php?id=62174) (2011, "A feature for semi-sync replication"), from a search excerpt only. It asked for commits to be held until a replica receives the binlog, because "another 'new thread' still can read the data generated by this transaction". bugs.mysql.com was blocked in this session.
- MySQL Bug [#83158](https://bugs.mysql.com/bug.php?id=83158) ("Phantom-read problem in semi-sync loss-less replication"), from a search excerpt only. It reports a phantom read through crash and recovery even in lossless mode, and proposes new hook points. Status is Verified in the snapshot seen.
- MySQL blog archive, ["Semi-synchronous replication performance in MySQL 5.7"](https://dev.mysql.com/blog-archive/semi-synchronous-replication-performance-in-mysql-5-7/), from a search excerpt only. It credits "Yoshinori Matsunobu's suggestions" for loss-less semi-sync. dev.mysql.com was blocked in this session, so the manual was not read directly.

**Key primary-source detail:** a semi-sync timeout is not an error. In `commitTrx()`, the timeout path calls `switch_off()`, which wakes every waiting session, and the function still returns `0`. The client's COMMIT gets a normal OK. From then on the primary runs async, and the only signals are a log line and the `Rpl_semi_sync_source_no_tx` and `no_times` counters. This is true in 5.5, 5.6, 5.7 and 8.0, with the same 10000 ms default.

## LinkedIn Post

The primary crashed one second after the INSERT committed. A dashboard had already read the new row. The replica that got promoted had never seen it.

MySQL semi-synchronous replication allows this. People turn semi-sync on precisely so that a failover can't lose acknowledged writes. In MySQL 5.5 and 5.6, this was simply how it behaved.

The original plugin waited in one place. Its only waiting callback, repl_semi_report_commit, is registered under after_commit. The order was: write and sync the binlog, commit in InnoDB, then block the client until a replica confirms it received the event. That client waits. No other session does. InnoDB has already committed and released the row locks, so any reader can see the row.

That leaves a window where the data is visible on the primary and stored nowhere else. If the primary dies inside it, the writer never got its OK, and that part is fine. The reader, though, already acted on a row that the new primary doesn't have. A 2011 bug report (#62174) asked for this to be fixed.

MySQL 5.7.2 added rpl_semi_sync_master_wait_point with two values and made AFTER_SYNC the default. The wait moves to the after_sync hook, after the binlog sync and before the engine commit. In the plugin's own words, no other session "can see the effects of the transaction before the replica has received it." The MySQL team credits Yoshinori Matsunobu's suggestions for this "loss-less" mode.

That closed the visibility window. It didn't change the timeout.

rpl_semi_sync_master_timeout (rpl_semi_sync_source_timeout in 8.0) defaults to 10000 ms. If no replica acks in time, commitTrx() calls switch_off(), wakes every waiting session, and returns 0. The client gets an ordinary OK and nothing fails. The primary is now plain async, and the only trace is a log line plus Rpl_semi_sync_source_no_tx going up. It switches back on quietly once a replica catches up.

Crash recovery is a separate problem. Bug #83158 reports that readers can still hit a phantom row in lossless mode when the old primary restarts and recovers transactions that were never acked. It proposes new hook points for that.

Each fix made the window smaller and moved it. "A replica has it" holds until 10 seconds pass, or until the box restarts. If your failover runbook depends on that, alert on no_tx.

## Twitter Version

MySQL semi-sync in 5.5/5.6: InnoDB commits first, then the client waits for a replica ack.

Your client waits. Every other session can already read the row.

If the primary crashes in that gap and you promote the replica, someone has read a row that no longer exists.

5.7.2 added wait_point=AFTER_SYNC as the default, so the wait now happens before the engine commit.

Both modes share a catch: after 10,000 ms with no ack, the plugin calls switch_off(), wakes the waiters, and returns 0. COMMIT says OK and you're now running async. The only sign is Rpl_semi_sync_source_no_tx going up.

Alert on that counter.
